# 테라클린 제품 품질 개편 설계

2026-09-22 · 현재 작업 폴더의 소스 기준 · 구현 전 제안

## 1. 방향

**“무엇이 공간을 차지하는지 알고, 내가 고른 것만 정리한다.”**

홈페이지는 설치 여부를 판단하는 곳, 프로그램은 내 PC에서 다음 행동을 결정하는 곳으로 설계한다. 제품의 중심은 Windows 저장 공간 정리다. 생활 정리와 업체 연결은 유지하되 별도 진입점으로 옮긴다. 무료 PC 프로그램이라는 기존 사업 방향은 유지한다.

이번 산출물은 설계와 인터랙티브 시안이다. 기존 홈페이지·앱·파일 처리 로직은 수정하지 않았다. 시안의 모든 용량은 예시이며 실제 진단·삭제·다운로드를 수행하지 않는다.

## 3. 홈페이지

### 화면 순서와 문구

1. **첫 화면:** “비울 공간은 찾고. 중요한 파일은 남기고.” 설명은 “무엇이 공간을 차지하는지 살펴보고, 정리할 항목과 이유를 먼저 확인하세요.” 주 버튼은 Windows용 무료 다운로드, 보조 버튼은 예시로 살펴보기. 오른쪽에는 앱과 같은 결과 UI를 배치하고 예시 표시를 붙인다.
2. **어떻게 정리하는지:** 분석 → 이유와 영향 확인 → 선택 실행. 막연한 안전 배지 대신 한 항목의 실제 설명과 복구 조건을 보여준다.
3. **상황별 해결:** 공간이 부족할 때 / 같은 파일이 많을 때 / 다른 드라이브로 옮길 때. 시작프로그램 관리는 별도 부가 기능으로 소개한다. 부팅 속도나 회수량은 보장하지 않는다.
4. **신뢰:** 분석 위치, 파일 전송 여부, 작업별 되돌리기 범위, 업데이트 검증 방식. 통신이 있는 업데이트·선택적 통계와 파일 분석을 구분해 설명한다.
5. **설치 안내와 FAQ:** 지원 OS·아키텍처·버전·용량은 실제 릴리스 메타데이터와 검증 결과에서 표시. 최신 조회 실패 시 수치를 꾸미지 않고 공식 릴리스 경로 제공. 인증서 상태에 맞는 설치 안내 제공.
6. **마지막 다운로드:** 동일 버튼과 지원 환경. 하단에 도움말·업데이트 내역·개인정보·문의·생활 정리·제휴 링크.

브라우저 체험은 처음부터 “예시 데이터 체험”과 “내 폴더 분석”을 구분한다. 파일 선택 지원이 없는 브라우저에도 예시는 동작한다. 웹에서 사용할 수 없는 시스템 기능은 이유와 데스크톱 앱 경로를 표시한다.

### 시각 방향

따뜻한 흰색 배경, 진한 잉크색 제목, 짙은 녹색 행동 버튼. 큰 여백과 정확한 숫자를 중심으로 만든다. 첫 화면은 감정적인 일러스트 대신 실제 제품 화면을 사용한다. 최종 출시는 목업을 실제 앱 캡처로 교체한다.

- 본문 17~18px, 보조 14px 이상, 홈페이지 제목 64~76px / 모바일 38~44px.
- 앱 본문 16px, 제목 28~32px, 주요 용량 48~64px. 경로·숫자에만 고정폭 또는 숫자 폭 고정 적용.
- 홈페이지 최대 폭 1,200px. 앱 사이드바 216px, 내용 영역은 창 크기에 맞춰 유동 배치.
- 8px 간격 계열, 패널 모서리 16~24px, 기본 경계선 1px. 그림자는 대표 미리보기와 대화상자에 제한.
- 녹색은 선택·완료, 주황색은 확인 필요, 붉은색은 오류·파괴적 실행. 상태는 문구와 아이콘을 함께 표시.
- 키보드 포커스, 44px 버튼 높이, 축소 동작 설정, 본문 대비 4.5:1을 출시 기준으로 검증.

### 정보 구조

| 주 메뉴 | 담는 기능 | 첫 화면에서 사용자가 할 일 |
| --- | --- | --- |
| 내 PC | 드라이브 용량, 최근 진단, 추천 다음 작업 | 분석 범위를 확인하고 분석 시작 |
| 정리하기 | 추천 정리, 큰 파일, 중복 후보, 시스템 공간, 드라이브 이동, 프로그램 관리 | 추천 항목부터 검토하고 필요한 도구로 이동 |
| 기록과 복구 | 작업별 성공·실패·건너뜀, 되돌릴 수 있는 항목, 만료 조건 | 방금 실행한 결과 확인 또는 복구 |
| 설정 | 제외 폴더, 통계 선택, 업데이트, 도움말 | 사용자 정책 관리 |

생활 정리는 보조 메뉴로 유지한다. 업체 연결은 생활 정리 화면에서 사용자가 요청할 때 자연스럽게 연결하며 PC 진단 결과에 영업 카드를 끼워 넣지 않는다.

### 핵심 흐름

**처음 실행 → 분석 범위 확인 → 분석 → 결과 → 항목 상세 → 실행 확인 → 실행 결과 → 기록과 복구**

- 시작: C: 사용량과 남은 공간, “내 PC 분석하기”. 접근 권한이 없으면 상태 미확인으로 표시. 분석 전 예상 회수량을 만들지 않는다.
- 분석: 현재 단계·읽은 파일 수·경과 시간·중단 버튼. 전체량을 모르면 퍼센트를 만들지 않는다. 중단하면 부분 결과임을 명시한다.
- 결과: 바로 검토할 캐시 / 사용자가 판단할 자료 / 보호한 항목. 세 숫자를 모두 “확보 가능한 용량”으로 더하지 않는다.
- 상세: 무엇인지, 사용하는 프로그램, 왜 후보인지, 실행 영향, 복구 가능성, 원본 경로. 기본은 짧은 설명, 세부 근거는 펼치기.
- 확인: 선택 개수·대상 드라이브·예상 처리량·되돌릴 수 없는 작업을 한곳에서 확인. 재생성 가능한 캐시도 원본 복구는 불가능하다고 표시.
- 결과: 실제 처리 바이트와 디스크 여유 변화는 별도 표시. 사용 중·권한 없음·변경됨·취소됨을 분리한다. 실패한 항목만 다시 시도할 수 있다.
- 복구: 작업 날짜, 출처, 복구 대상, 기한. 충돌 시 덮어쓰지 않으며 대상 드라이브가 없으면 재연결 안내. 즉시 삭제는 복구 버튼을 제공하지 않는다.

## 5. 기능 품질과 구조

### 실행 계약

`ActionPlan`에 planId, createdAt, scope, 항목별 fingerprint, ruleId, operation, estimatedBytes, recoveryPolicy를 둔다. 실행 버튼은 사용자가 본 계획 ID와 선택한 항목 ID만 전송한다. 실행 시 파일 변경·권한·대상 공간을 다시 확인한다. 새 파일이 나타나도 이전 승인에 끼워 넣지 않는다.

`ActionResult`는 succeeded / skipped / failed / cancelled, reasonCode, processedBytes, diskFreeBefore/After, recoveryEntryId를 반환한다. 용량은 엔진 계약에서 바이트로 유지하며 UI에서만 단위를 바꾼다. 다른 프로세스가 디스크를 사용하므로 여유 공간 증감을 전부 테라클린 성과로 단정하지 않는다.

중복 후보는 크기 → 부분 해시 → 전체 내용 검증 순서로 좁힌다. 확인 과정에서 변경된 파일은 다시 검증한다. 원본이라는 단정 대신 “남길 파일”이라고 표시하고 사용자가 선택한다. 하드링크·드라이브 이동은 별도 복구 정책과 장부를 유지한다.

### 모듈 구성 제안

`web/src/ui/` 공통 버튼·대화상자·상태 패널, `web/src/features/` dashboard / cleanup / duplicates / history, `web/src/services/` desktop-engine / browser-engine, `web/src/state/` scan-session / action-session으로 점진 분리한다. 초기에는 현재 엔진 명령을 어댑터로 감싸고, 한 번에 엔진을 교체하지 않는다. 홈페이지·앱은 색상·타입·버튼과 제품 결과 카드 표현을 공유한다.

작업 로그는 로컬 우선이며 경로가 외부 통계로 나가지 않도록 한다. 지표 수집이 필요하면 기존 동의 정책을 검토하고 최소 이벤트만 선택 수집한다. 분석 원시 데이터는 자동 전송하지 않는다.

## 6. 구현 순서와 완료 기준

| 단계 | 범위 | 완료 기준 |
| --- | --- | --- |
| P0 — 동작과 약속 정합성 | 복구 문구 정리, 부분 해시/전체 검증, 승인 계획 연결, 용량 계약 | 문구가 실제 동작과 일치하고 변경된 파일·중간 내용이 다른 파일이 잘못 처리되지 않음 |
| P1 — 대표 경험 | 디자인 토큰, 홈페이지, 내 PC → 분석 → 결과 → 확인 → 실행 | 웹·데스크톱 대표 흐름이 같은 시각 체계로 동작. 예시와 실데이터 구분 |
| P2 — 전체 도구 정리 | 중복·이동·시스템 공간·시작프로그램·프로그램·기록과 복구 | 기존 기능 접근 경로 보존. 실패·취소·복구 충돌 시나리오 통과 |
| P3 — 출시 품질 | 실제 캡처, 설치·업데이트, 반응형·키보드·성능·안내 문서 | 깨끗한 Windows 환경에서 설치 → 분석 → 실행 → 복구 → 업데이트 검증 |

기간은 설계 범위 제안으로 1인 개발 약 3~4주를 가정하되, P0의 기존 동작 검증 후 다시 산정한다. 단순 색상 변경으로 끝내지 않고 P1을 첫 리뷰 가능한 버전으로 묶는다.

검증은 임시 파일과 별도 시험 환경에서 진행한다. 시스템의 실제 사용자 파일로 삭제 테스트를 하지 않는다. 기존 엔진 회귀 테스트에 더해 파일 중간만 다른 중복 후보, 승인 후 변경, 부분 성공, 이동 충돌, 복구 충돌을 검증한다. 성능은 정해진 표본·디스크·파일 수로 첫 화면 표시와 분석 시간을 기록하고 기존 대비 개선을 측정한다. 현재 측정 없이 “몇 배 빠름” 같은 목표를 성과로 쓰지 않는다.

홈페이지는 390/768/1440px, 앱은 현재 최소 창 820×520 및 기본 1180×640, 배율 125/150%, 키보드 조작을 확인한다. 다운로드는 실제 비인증 사용자 조건에서 최종 설치파일까지 검증한다.

## 7. 시안 보는 법

`index.html`을 열면 홈페이지 시안이 나온다. 상단의 프로그램 시안에서 결과·상세·실행 확인·예시 완료·기록 화면을 살펴볼 수 있다. 수치와 실행은 고정 예시다. 이 시안은 주요 방향을 검토하기 위한 것으로 실제 스캔 진행·오류·설정·기타 도구 전체를 구현한 것은 아니다.
