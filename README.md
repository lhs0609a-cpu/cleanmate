# 클린PT (CleanPT) — 정리도 PT가 필요합니다

> 트레이너가 대신 운동해주지 않듯, 대신 다 지워버리지 않는다.
> 지워도 되는 것과 건드리면 안 되는 것을 **알려주고 함께 정리한다.**

**사업 방향.** PC 정리 프로그램은 **무료**다. 여기서 돈을 벌지 않는다.
정리의 첫 단계를 무료로 열어 두고, 그다음 단계 — 청소 업체, 정리정돈(정리수납) 전문가 —
연결에서 수익을 낸다. 그래서 프로그램에 결제 유도나 광고를 넣을 이유가 구조적으로 없다.
랜딩의 `#roadmap` 섹션이 이 3단계를 그대로 보여준다(2·3단계는 "준비 중"으로 정직하게 표시).

기획: [마스터 기획서](https://claude.ai/code/artifact/4e328b41-b571-44f5-9915-61481e4a4692) ·

## 배포

GitHub → Vercel 자동 배포. `master`에 푸시하면 프로덕션에 나간다.

### CSP는 페이지별로 다르다 (한 덩어리로 묶으면 깨진다)

`vercel.json`이 문서마다 다른 `connect-src`를 준다. 두 페이지가 원하는 게 정반대다.

| 문서 | `connect-src` | 왜 |
| --- | --- | --- |
| `/app.html` | `'none'` | 사용자 파일을 읽는 화면. 브라우저가 네트워크를 **강제 차단**한다. *"파일은 기기를 떠나지 않습니다"* 를 말이 아니라 배포 설정으로 증명한다 — 우리 코드가 보내려 해도 막힌다. |
| 그 외(랜딩) | `https://api.github.com` | 사용자 파일을 안 읽는다. 최신 릴리스 버전·다운로드 URL을 읽어야 한다(`web/src/landing.ts`). |

> 전에는 `/(.*)` 하나에 `'none'`을 걸어 랜딩의 최신버전 조회가 **조용히 전부 실패**했다
> (`try/catch` 폴백이 있어 에러 없이 "릴리스 페이지에서 받기"로 떨어졌다). 정책을
> 합치면 둘 중 하나는 반드시 깨진다.

### 자동 업데이트 무결성

업데이트는 우리가 사용자 컴퓨터에서 코드를 실행하는 통로다. 그래서 3중으로 잠근다.

1. CI가 설치파일의 **SHA-256을 계산해 `latest.json`의 `signature`에 넣고** 릴리스에 함께 올린다
   (`release.yml`). 서명 계산이 실패하면 릴리스를 내지 않는다. 서명은 코드서명 **뒤에** 계산한다 —
   서명하면 파일이 바뀐다.
2. 앱이 그 `latest.json`을 읽어, 받은 파일의 해시와 대조한다
   (`src/updater.ts`의 `verifyIntegrity` — 순수 함수, 테스트됨).
3. Rust가 **실행 직전에 한 번 더** 대조한다(`src-tauri/src/main.rs`). 불일치면 실행하지 않고 파일을 지운다.

**fail closed** — 서명이 없거나 형식이 깨졌으면 "검증 불가라 통과"가 아니라 **거절**이다.

### 코드 서명

`CODESIGN_PFX_BASE64` · `CODESIGN_PFX_PASSWORD` 시크릿이 있으면 CI가 앱 바이너리와
설치파일을 서명한다. 없으면 그 단계를 건너뛰고 빌드는 계속된다(서명 없이 나가면 첫 실행 때
SmartScreen "알 수 없는 게시자" 경고가 뜬다).

### 브랜드 자산

`node scripts/make-brand.mjs` → `web/public/`의 `og.png`(링크 공유 썸네일)·파비콘.
이 환경엔 이미지 도구도 폰트 래스터라이저도 없어서 SDF 도형 + 획 폰트로 직접 굽는다.
CI도 빌드 전에 이걸 돌려 소스와 어긋나지 않게 한다.

## ★ 스캐너는 숨은 공간을 볼 수 없다 (실측)

```bash
npm run probe   # 숨은 공간 프로브 (읽기 전용)
```

개발 PC 실측: `readdir`는 `hiberfil.sys`·`pagefile.sys`·`swapfile.sys`를 전부 봤지만
`stat()`이 셋 다 **EPERM**으로 튕겼다. 시스템이 파일을 독점 잠금해서 열 수 없다.
그러면 `scanner.ts`가 이걸 `skipped`로 보내버려서 `files[]`에 못 들어오고,
분류도 엔진도 질문도 이 파일들을 **영원히 못 본다**.

| | |
|---|---|
| 이 PC의 hiberfil + pagefile | **40.7GB** |
| 우리 엔진에 보이는 양 | **0** |

기획서 17장이 *"파일트리 스캔이 못 보는 숨은 공간"* 이라고 쓴 게 우리 코드에서 그대로
재현됐다. **숨은 공간은 스캐너를 고쳐서 될 일이 아니라 별도 프로브로 가야 한다**는 게
실측으로 확정됐다.

부수 발견 — `paths.ts`의 `win.pagefile-hiberfil` 규칙은 셋을 한 덩어리로 잠근다.
그런데 셋은 `usedBy`가 전부 다르다(hiberfil=최대절전·빠른시작 / pagefile=가상메모리 /
swapfile=스토어앱). **설명을 쓰려고 하니 규칙이 뭉개져 있다는 게 드러났다** —
"설명이 곧 규칙 감사"가 첫날부터 작동했다.

### hiberfil — 설명 레이어의 첫 사례

리서치가 주장한 *"hiberfil은 RAM의 ~40%"* 를 실측으로 확인: RAM 31.7GB → **12.7GB (40.0%)**.
설명은 정적 문자열이 아니라 실측에서 생성된다 — RAM 크기, 노트북/데스크톱(섀시+배터리
독립 2신호), 빠른 시작 여부, 사용자 지정 크기에 따라 달라진다. *"당신 PC 얘기"* 여야
마음이 놓이지 일반론은 위키백과다.

지역화 함정도 잡았다: `powercfg /a` 출력은 한국어라 파싱하면 다른 언어 윈도우에서 깨진다.
→ 언어 무관 신호만 쓴다. **`hiberfil.sys`의 존재 자체가 최대절전이 켜졌다는 증거**다.

## 설계

```
probes/        숨은 공간. 스캔과 별개 경로 — 파일 트리에 안 보이기 때문에.
  facts.ts       시스템 사실 수집(판단 없음)
  hiberfil.ts    발견 + 7문답 설명 + 되돌릴 수 있는 회수 명령

scanner.ts     원시 사실만 수집. 판단 없음. (나중에 MFT로 교체)
  ↓
classify.ts    3-존 판정. 규칙 확증분만 존 A 자격 (R1 방어선)
  ↓
engine.ts      미지수 클러스터링 → 레버리지 점수 → 질문 3~4개
  또는
sweep.ts       존 A 자동 정리 계획 → 격리 (미리보기가 기본)
  ↓
quarantine.ts  이동 + 장부. 30일 유예. 복구. ★유일한 영구삭제 지점
```

### 삭제는 4단계다

```
후보 지정 → [격리] → 30일 유예 → 실제 삭제
             ↑ "지웠어요"라고 말하는 시점    ↑ 진짜 지우는 시점
```

이 시차가 안전의 전부다. CleanMyMac이 Alfred 워크플로를 날린 건 이 시차가 없어서다.

- **격리 폴더는 원본과 같은 드라이브에** — 같은 드라이브면 rename이 즉시고 공짜다.
  드라이브를 넘으면 복사+삭제라 40GB에 몇 분씩 걸리고 순간 공간이 두 배로 필요하다.
  격리하겠다고 디스크를 꽉 채울 순 없다
- **장부도 그 드라이브에** — 중앙 장부는 외장을 뽑으면 실물과 어긋난다
- **장부는 이동 뒤에 적는다** — 먼저 적고 이동에 실패하면 유령이 남고, 복구가 그 유령을
  되살리려다 실패한다
- **부분 성공을 허용한다** — 억지 원자성보다 "뭐가 됐고 뭐가 안 됐는지 정직한 보고"
- **되돌릴 자리를 누가 차지했으면 덮어쓰지 않는다** — 되돌리려다 남의 파일을 날리면
  격리의 존재 이유가 사라진다
- **영구삭제는 `purgeExpired` 한 곳에만** — 호출자가 "지금 지워줘"라고 요청할 방법이 없다

**knowledge/paths.ts 가 제품의 핵심 자산이다.** 두꺼울수록 콜드스타트(R2)가 해결되고
LLM 오분류(R1)에 덜 의존한다. 그리고 이건 **설명 자산이기도 하다** — 경쟁사는
사실 DB가 없어서 LLM을 붙이면 환각이 나온다. 해자가 두 겹이다.

### 설명 레이어 — "마음놓고 지우려면"

사람이 삭제 전에 실제로 묻는 건 7가지다. 한 줄짜리 `reason`으로는 1.5개밖에 못 답하고,
못 답하는 것들이 정확히 사람이 무서워하는 것들이다.

> ① 이게 뭐야 · ② 왜 이렇게 커 · **③ 뭐가 이걸 쓰고 있어** · ④⑤ 지우면 뭐가 달라져 ·
> ⑥ 되돌릴 수 있어 · ⑦ 안 지우면 어떻게 돼

- **사실은 DB, 표현만 LLM.** 설명은 사용자가 검색해서 검증할 수 있다. 한 번 지어내면
  신뢰가 끝난다. `engine.ts`의 질문 선정과 같은 원칙 — LLM에 판단 권한을 주지 않는다
- **★ `usedBy`를 못 쓰는 규칙은 SAFE 자격이 없다.** "뭐가 이걸 쓰는지" 모른다 =
  "뭐가 깨지는지" 모른다는 뜻이다. Alfred 워크플로 참사도 DriveFS 26.5GB 오탐도
  전부 이걸 몰라서 났다. **설명을 강제하면 엉터리 SAFE 규칙이 구조적으로 못 들어온다**
- **양면 정직** — 손해를 반드시 쓴다(hiberfil은 "부팅 2~5초 느려짐"). 좋은 점만 쓰면 광고다
- **`ifKept` 필수** — "안 지워도 된다"는 선택지를 절대 뺏지 않는다. 없으면 압박이 된다

### 안전 불변식

- 모르는 파일은 **절대 SAFE로 추측하지 않는다** → AMBIG(물어봄). 추론은 자동 처리 자격 없음
- 질문의 답은 **재분류만** 한다. 어떤 답도 즉시 삭제를 유발하지 않는다
- '아니오/모르겠음'은 **항상 보존 쪽으로** 폴백
- 존 C는 스캔조차 하지 않는다(`SKIP_DIRS`) — 실수의 여지를 원천 차단
- **미리보기가 기본이다.** `--apply` 없이는 아무것도 안 움직인다 (숨은 원탭 삭제 금지)
- **삭제 직전 재검증** — 계획과 실행 사이에 파일이 바뀌었으면 건너뛴다.
  사용자가 승인한 파일과 지금 파일이 다른 파일일 수 있다 (TOCTOU)
- 자동 정리는 **`isAutoEligible`이 통과시킨 것만** — 규칙 확증분. 추론은 무인 삭제 안 함

### ★ 실측으로 잡은 버그: 안 건드린 파일의 절반이 거부됐다

E2E에서 캐시 파일 5개 중 3개가 *"스캔한 뒤에 파일이 바뀌었어요"* 로 거부됐다.
아무도 안 건드린 파일인데. 그리고 **무작위였다**.

```
raw mtimeMs           = 1784276323518.8796
Stats.mtime.getTime() = 1784276323519    ← node가 Math.round 해서 Date를 만든다
Math.floor(raw)       = 1784276323518    ← 옛 비교 코드
                        519 !== 518 → 멀쩡한 파일을 거부
```

`sweep`은 `mtime.getTime()`(반올림)으로 저장하고 `quarantine`은 `Math.floor(mtimeMs)`
(내림)로 비교했다. **소수부가 0.5 이상인 파일마다 터진다** — 그래서 절반이 무작위로 거부됐다.
(스펙상 `new Date(x)`는 절삭이지만, node는 Date를 만들기 **전에** 이미 반올림한다)

→ `stampMtime()` 하나로 양쪽을 강제 통일. 비교하는 두 값이 서로 다른 방식으로
만들어질 여지를 없앴다. 회귀 테스트는 그때 실제로 나온 값을 그대로 박아뒀다.

교훈: **재검증은 과민해도 죽고 둔감해도 죽는다.** 과민하면 아무것도 못 지우고
(사용자는 "왜 안 지워지지?"), 둔감하면 방금 고친 파일을 지운다. 그래서 이 판단을
순수 함수(`isUnchanged`)로 빼서 테스트가 직접 겨냥할 수 있게 했다.
