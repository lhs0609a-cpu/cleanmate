# 엔진에서 배포까지 — 전체 설계

> 지금: 터미널에서 도는 **엔진**(분류·격리·복구·프로브)이 완성돼 있다.
> 목표: 일반 사용자가 **다운로드 → 설치 → 더블클릭 → 원클릭 최적화 → 자동 업데이트**
> 하는 **프로그램**.
>
> 이 문서는 그 사이의 모든 것을 설계한다. 순서가 곧 원칙이다 — 포장(이노셋업)·
> 자동 업데이트는 맨 마지막이다. 포장할 알맹이(화면 있는 앱)가 먼저다.

---

## 0. 지금 가진 것 (설계의 출발점)

```
src/
  scanner.ts      폴더 순회 → 원시 사실           (판단 없음)
  classify.ts     3-존 분류 (SAFE/AMBIG/LOCKED)   (R1 방어선)
  knowledge/      경로 지식 DB — 핵심 자산
  engine.ts       미지수 클러스터 → 질문 3~4개
  sweep.ts        존 A 자동 정리 계획 → 격리
  quarantine.ts   이동 + 장부 + 30일 유예 + 복구   (유일한 영구삭제 지점)
  probes/         숨은 공간 (hiberfil 등)
  cli-*.ts        터미널 껍데기 5개
```

**결정적 사실: 엔진은 외부 의존성이 0이다.** Node 내장 모듈(`fs`,`path`,`crypto`,
`child_process`)만 쓴다. → 단일 실행파일로 포장하기 쉽고, 어떤 껍데기에도 넣을 수 있다.

로직(`scanner`~`quarantine`)과 껍데기(`cli-*`)가 이미 분리돼 있다.
**화면을 붙인다 = `cli-*`를 GUI로 갈아끼운다.** 엔진은 손대지 않는다.

## 2. ★ 핵심 결정: 앱을 무엇으로 만드나

엔진은 TypeScript(Node)다. 화면 있는 데스크톱 앱으로 만드는 길은 셋이다.

| 방식 | 껍데기 | 엔진 처리 | 설치 크기 | 재작성 |
|---|---|---|---|---|
| **A. Tauri + Node 사이드카** | Rust + 시스템 웹뷰 | 엔진을 단일 exe로 포장해 옆에 태움 | ~10MB | **없음** |
| B. Electron | Node + 크로미움 내장 | 엔진이 그냥 안에서 돎 | ~120MB | 없음 |
| C. Rust 전면 재작성 | Rust + 웹뷰 | 엔진을 Rust로 다시 씀 | ~10MB | **전부** |

### 결정: **A. Tauri + Node 사이드카** (지금), C로 점진 이전 (나중)

**왜 A인가:**
- **재작성 0.** 테스트 30개 통과한 엔진을 그대로 쓴다. 오늘 잡은 mtime 버그 같은
  걸 다시 겪지 않는다.
- **설치가 가볍다(~10MB).** 신뢰·프라이버시가 제품의 얼굴인데, 120MB짜리 클리너는
  그 자체로 모순이다. Electron은 크로미움을 통째로 넣는다.
- **README의 최종 방향과 일치.** "최종은 Rust 코어 + Tauri." A는 그 길의 1단계다.
- **자동 업데이트가 공짜.** Tauri에 서명 검증까지 되는 업데이터가 내장돼 있다(§7).

**"사이드카"가 뭔가:** 엔진(TS→JS)을 **Node SEA**로 단일 `.exe`(`cleanmate-engine.exe`)로
구워서 Tauri 앱 안에 함께 넣는다. 화면(Rust)이 이 엔진 exe를 자식 프로세스로
불러 명령을 주고 JSON을 받는다. 엔진은 의존성이 0이라 SEA 포장이 깔끔하다.

**트레이드오프 (정직하게):** 사이드카 포장은 "엔진 exe 굽기 + Tauri에 태우기"라는
빌드 단계가 하나 는다(§6에서 설계). Electron이었으면 그 단계가 없다. 하지만 그 대가로
설치 크기 10배와 재작성을 피한다 — 그만한 값어치가 있다.

**나중에 C로 왜 가나:** 스캐너가 병목이다(39만 파일 33초, Node fs 재귀).
README대로 **스캐너만** Rust MFT 직접 읽기로 바꾸면 수초로 준다. 엔진 전체가 아니라
`scanner.ts`만. 나머지(분류·격리·질문)는 성능 병목이 아니니 TS로 오래 남아도 된다.
Tauri를 이미 쓰고 있으면 이 이전이 매끄럽다 — 껍데기를 안 바꾸니까.

## 3. ★ 권한 모델 (신뢰의 핵심 — 절대 타협 안 함)

**앱은 기본적으로 관리자 권한 없이 돈다.**

- 사용자 캐시 정리(`AppData`), 다운로드 정리, 스캔 → **관리자 필요 없음.** 대부분이 여기.
- 시스템 작업(hiberfil `powercfg`, WinSxS `DISM`, 복원지점 `vssadmin`) → **그때만** 승격.

**왜 전체를 관리자로 안 띄우나:**
- 최소 권한 원칙. 캐시 지우자고 시스템 전체 권한을 잡는 건 과하다.
- "이 앱이 관리자 권한을 항상 요구한다"는 그 자체로 불신 신호다. CCleaner류가 그렇다.
- 실수의 폭발 반경을 줄인다. 버그가 나도 관리자가 아니면 시스템을 못 망친다.

**어떻게 승격하나:** 시스템 작업이 필요한 순간에만, "이 작업은 관리자 권한이 필요해요"를
설명하고 **UAC 프롬프트를 그 작업에 대해서만** 띄운다(별도 승격 헬퍼 프로세스).
사용자가 무슨 권한을, 왜, 언제 주는지 안다.

## 4. 화면 설계 (MVP는 5개)

### 4.1 홈 (대시보드)
```
┌────────────────────────────────────────────┐
│  테라클린                           ⚙ 설정  │
│                                             │
│     이 PC에서 정리 가능:  14.6 GB            │
│     ▓▓▓▓▓▓▓▓░░░░░░░░  디스크 320/500GB       │
│                                             │
│        ┌──────────────────────┐             │
│        │   원클릭 최적화        │  ← 핵심 버튼 │
│        └──────────────────────┘             │
│                                             │
│   ✓ 지켜드린 것: 41.5GB  (자세히)            │  ← 경쟁사가 못 하는 말
│   ↺ 격리함: 1.9GB · 28일 남음  (되돌리기)     │
└────────────────────────────────────────────┘
```

### 4.2 최적화 결과 (원클릭 후)
- "지금 즉시 확보 / 30일 뒤 최종 / 숨은 공간에서 회수 가능" 3분할 (거짓말 안 함)
- 무엇을·왜 정리했는지 항목별로 펼쳐볼 수 있음 (숨은 원탭 삭제 금지)

### 4.3 질문 (존 B — "물어보고 지우기")
- 엔진의 `Question`을 카드로. 예/아니오/하나씩 버튼.
- 각 카드에 "왜 묻나" 항상 표시.
- ★ 이 화면이 붙어야 답변 루프가 생긴다 = 제품의 핵심 가정(대화형 UX)을 처음 측정.

### 4.4 숨은 공간 (프로브)
- hiberfil 등. 7문답 설명(이미 있음)을 펼침 카드로.
- "끄기" 버튼 → 여기서 UAC 승격 → `powercfg` 실행 → 되돌리기 버튼.

### 4.5 격리함 (되돌리기 센터)
- 격리된 항목, 남은 유예일, 격리 이유(감사 로그).
- **되돌리기는 항상 한 번에.** BleachBit이 undo가 없어 죽은 자리다.

**나중:** 투명 결제 화면(16.1), 자동 유지 설정(16.2), 효과 대시보드 이력.

## 5. "원클릭 최적화"의 정직한 정의

우리 안전 원칙은 "숨은 원탭 삭제 금지"다. "원클릭"과 충돌하는 것 같지만 아니다.

**원클릭 = 이 세 가지를 한 번에 한다:**
1. **존 A(규칙 확증 캐시)를 격리로 정리** — 이건 진짜 안전. 재생성되고, 되돌릴 수 있음.
2. **숨은 공간을 찾아서 보여줌** — 실행은 안 함, 발견만. (hiberfil은 조건부라 물어봐야)
3. **존 B 질문을 수면 위로** — "물어볼 게 3개 있어요"

즉 원클릭은 **"확실한 건 알아서 하고, 애매한 건 모아서 보여준다."**
확실한 것만 자동 실행하고, 나머지는 사용자 앞에 정직하게 놓는다.
이게 "원클릭의 편함"과 "숨은 삭제 금지"를 동시에 지키는 유일한 정의다.

## 6. 빌드 파이프라인

```
[1] TS 엔진 → 번들
    esbuild로 src/*.ts를 JS 한 덩어리로 (의존성 0이라 간단)
       ↓
[2] JS → 단일 exe
    Node SEA → cleanmate-engine.exe  (Node 런타임 내장, 설치 불필요)
       ↓
[3] Tauri 앱 빌드
    화면(웹) + Rust 껍데기 + [2]를 사이드카로 포함
       ↓
[4] 설치 프로그램 생성
    Tauri가 NSIS(.exe) + MSI(.msi) 자동 생성
       ↓
[5] 코드 서명 (§8)
       ↓
[6] GitHub Releases 업로드 + 업데이트 매니페스트 갱신 (§7)
```

전부 CI(GitHub Actions)에서 자동화한다. `git tag v1.0.1` 밀면 [1]~[6]이 자동으로 돈다.

## 7. 자동 업데이트 — V3/알약 방식 (이노셋업 + 조용한 재설치)

**결정: Tauri 내장 업데이터가 아니라, 이노셋업 설치파일을 조용히 재실행하는 방식.**
V3·알약이 실제로 쓰는 그 방식이고, "이노셋업으로 배포"라는 결정과 자연스럽게 한 쌍이다.

```
앱 실행 → latest.json 확인 → 내 버전보다 높으면
  → 이노셋업 설치파일 다운로드 → /VERYSILENT 로 조용히 재설치 → 앱 재시작
```

- **장부(`latest.json`)**: 최신 버전·다운로드 URL을 담은 정적 JSON. GitHub Releases에 둔다.
  서버 불필요. CI가 릴리스마다 자동 갱신(§6).
- **판단은 순수 로직**(`src/updater.ts`) — `compareVersions`로 SemVer 비교. 같은 버전이면
  절대 재설치 안 함(무한 재설치 방지), 낮은 버전이면 다운그레이드 안 함. 테스트로 잠금.
- **실행은 데스크톱 셸**(`src-tauri/src/main.rs`의 `download_update`·`apply_update`) — 받아서
  `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART` 로 재설치. 이노셋업이 실행 중인 앱을 닫고
  덮어쓴 뒤 `--updated`로 재시작. (`installer/cleanmate.iss`)

**코드 서명(Authenticode)은 별개다(§8).** 위 흐름은 "업데이트를 어떻게 적용하나"이고,
서명은 "이 설치파일이 진짜 우리 것인가"를 윈도우에 증명하는 것이다. 서명이 없으면
자동 업데이트의 조용한 재설치를 윈도우가 경고로 막을 수 있다 — 그래서 배포 전 필수다.

## 8. ★ 코드 서명 (신뢰우선 제품엔 선택이 아니라 필수)

**서명 안 하면 어떻게 되나:** 사용자가 설치할 때 파란 전체화면 경고 —
*"Windows의 PC 보호 · 알 수 없는 게시자"* — 가 뜬다. "실행하지 않음"이 기본 버튼이다.

정리·삭제 프로그램은 안 그래도 의심받는데, 첫 화면이 보안 경고면 **신뢰우선 제품이
시작부터 진다.** 우리가 이기려는 그 지점에서.

**필요한 것:** 코드 서명 인증서 (Authenticode)
- OV 인증서: 연 십수만 원대. 평판(SmartScreen)이 쌓이는 데 시간이 걸림.
- EV 인증서: 더 비쌈. 즉시 SmartScreen 신뢰. USB 토큰 필요.
- → **초기엔 OV로 시작**하고 다운로드가 쌓이며 평판을 올리는 게 현실적.

**이건 예산 결정이다.** 코드보다 먼저 정해야 자동 업데이트·배포가 완성된다.
(서명 없이 내부 테스트까지는 가능. 공개 배포 직전에 반드시 필요.)

## 9. 설치 프로그램: Tauri 기본 vs 이노셋업

**정직하게: Tauri가 NSIS 설치 마법사를 이미 자동 생성한다.** "다음 > 다음 > 완료",
바탕화면 아이콘, 제거 프로그램 등록, WebView2 자동 설치까지 다 된다.
**대부분의 경우 이노셋업이 따로 필요 없다.**

**이노셋업을 쓸 이유가 생긴다면:**
- 설치 중 커스텀 UX(사용권 동의 흐름, 옵션 선택, 마이그레이션)가 복잡해질 때
- 한국 사용자 대상 특수 처리(특정 백신 예외 안내 등)

**결정(변경됨): 이노셋업으로 간다.** 자동 업데이트를 §7의 "조용한 재설치" 방식으로
직접 배선했으므로(`updater.ts` + `main.rs`), 이노셋업과 자동 업데이트가 한 쌍으로 맞물린다.
이게 V3/알약과 같은 구조다. 자산·구성은 §13 참고.

## 10. 배포

- **다운로드**: GitHub Releases에 서명된 설치파일 업로드. 홈페이지(이미 Vercel에 있음)에
  "다운로드" 버튼 → 최신 릴리스로 링크.
- **버전 규칙**: SemVer. `git tag v1.0.1` → CI가 빌드·서명·릴리스·매니페스트 갱신.
- **웹 데모의 역할**: 지금 Vercel 데모는 "이런 걸 만든다"는 랜딩 + 브라우저 체험용.
  실제 앱은 여기서 **다운로드**로 연결. (브라우저는 파일을 못 지우므로 데모는 분석까지만.)

## 11. 로드맵 (순서 = 원칙)

```
✅ 0. 엔진 + 안전(격리/복구)          ← 지금 여기
   1. 화면(Tauri) + 엔진 사이드카 연결  ← 다음. "눈으로 보임"
   2. 원클릭 최적화 버튼 (존 A 자동 + 발견)
   3. 답변 루프 (존 B — 물어보고 지우기) ★핵심 가정 첫 측정
   4. 숨은 공간 실행 (hiberfil 끄기 + UAC 승격 + 되돌리기)
   5. 감사 로그 (복구·삭제 이력)
   ── 여기까지가 "쓸 수 있는 앱" ──
   6. 빌드 파이프라인 (SEA → Tauri → NSIS)
   7. 코드 서명 (예산 결정 필요)
   8. 자동 업데이트 (Tauri 업데이터 + 매니페스트)
   9. 배포 (GitHub Releases + 홈페이지 다운로드)
   ── 여기까지가 "배포된 제품" ──
   나중. 이노셋업(필요시) · Rust 스캐너 · 투명결제 · 자동유지
```

**왜 이 순서인가:** 1~5는 "쓸 수 있는가", 6~9는 "남에게 줄 수 있는가"다.
쓸 수 없는 걸 포장부터 하면 빈 상자다. 화면(1)이 제일 먼저인 이유는, 지금
**만든 사람조차 엔진을 터미널로만 볼 수 있어서** 진짜 쓸만한지 감이 안 오기 때문이다.

## 12. 지금 정해야 할 열린 결정

1. **껍데기: Tauri 확정?** (권고: 예. 가볍고 재작성 없고 README 방향과 일치)
2. **코드 서명 예산** — OV 인증서 연 비용을 감당할지. 공개 배포 전 필수. (테스트까진 불필요)
3. **이노셋업 정말 쓸지** — 권고: 1단계는 Tauri 기본 NSIS. 이노셋업은 나중에 필요하면.

1·3은 권고대로 가도 되고, 2는 배포(9단계) 전까지만 정하면 된다.
그래서 지금 당장은 **1단계(화면)부터 만들면 되고**, 예산 결정이 개발을 막지 않는다.

## 13. 구현 현황 — 이번에 세운 것 / 남은 것

### 세운 것 (코드로 존재, 테스트·검증됨)
- `installer/cleanmate.iss` — 이노셋업. 자동설치·자동시작(상주)·무인 재설치 지원.
- `src/updater.ts` (+테스트) — 업데이트 판단 로직. SemVer 비교, 무한 재설치·다운그레이드 방지.
- `updater/latest.json` — 업데이트 장부 형식.
- `src-tauri/` — Tauri v2 셸(창 + `download_update`/`apply_update` 명령).
- `.github/workflows/release.yml` — CI. 태그 밀면 클라우드에서 빌드→설치파일→릴리스.

### 첫 빌드 전에 필요한 것 (전제)
1. **브랜드 아이콘** — 로고 PNG 하나(`assets/logo.png`). CI가 `tauri icon`으로 전 크기 생성.
   없으면 빌드가 아이콘 단계에서 막힌다. 제품의 얼굴이라 어차피 필요한 자산.
2. **첫 CI 빌드 반복** — Rust 셸은 로컬에서 컴파일 검증을 못 했다(이 PC에 Rust 없음 +
   드라이브 폴더 빌드 불가). 첫 태그 빌드가 진짜 시험이고, 1~2회 수정이 정상이다.
3. **코드 서명 결정** — §8. 없으면 내부 테스트까지는 되지만, 공개 배포·조용한 자동
   업데이트에는 필수. 예산 결정.

### 빌드/배포를 어디서 하나
- **릴리스는 CI(클라우드)에서.** 로컬에 Rust·빌드도구를 안 깔아도 된다. 드라이브 폴더의
  빌드 문제도 CI에는 없다(깨끗한 환경에서 새로 install).
- **로컬 개발(선택)** — 빠른 반복을 원하면 `C:\dev\cleanmate`에 클론 + Rust/Node 설치 후
  `npm run app:dev`. README의 "로컬 클론에서 작업" 원칙과 같다.
